NEOP — End-to-End Technical Plan, with scrutiny

25 September 2026 · Mansi Gambhir · Companion to NEOP-ARCH-001

5blocking findings 9before second app 6clean-ups ~17weeks · 7 phases

Summary

The v2 picture is sound at its core and should be built, but not as drawn: it has five defects that will bite in the Ledger pilot and eight smaller contradictions. The core is right — a durable job/proposal book per app, a model-free execution path after a human yes, a gate the model cannot edit, and one platform gateway minting execution tokens.

What NEOP is, in one line: a per-subject app whose always-on runner turns every request into a job in its own Postgres table family, spawns a keyless assistant per job, routes every effect through a template-owned gate, and parks the job on a fingerprinted proposal until a person answers through the platform.

Top five fixes before implementation (detail in Scrutiny):

  1. Tenant isolation inside a family is missing. Roles isolate apps from each other, but every company's rows share ledger__*. Add company_id NOT NULL everywhere plus row-level security keyed off the verified gateway token.
  2. The wake races the execution. Section 6 sets the wait to ready at resolve, before carry out runs. The assistant can wake with no proof. The wait must turn ready only on DONE, DROPPED or EXECUTION_FAILED.
  3. Chat is a second, unauthenticated front door. Matrix pushes straight to the runner and results are lifted back from the room (6b). Both bypass the gateway and contradict "the room is the mirror, the book is the truth". Inbound and results must be typed, signed gateway calls.
  4. Package handler isolation cannot be enforced in-process. "No fetch, no filesystem" is a promise, not a wall, inside a Node backend. Run package handlers in a separate sandbox (subprocess with Deno permissions or isolated-vm).
  5. "Exactly once" is overclaimed. Social, email and payment APIs rarely offer idempotency keys. Specify at-least-once plus door-level idempotency plus read-back reconciliation, with an UNKNOWN outcome state.

Build order: decisions (1 week) → Ledger core without Matrix (3 weeks) → approvals and gateway-lite end to end (3 weeks) → rooms and bridge (2 weeks) → second app and borrowing (3 weeks) → registry and packages (3 weeks) → hardening (2 weeks). About 17 weeks for a four-engineer team.

Scope, principles and trust boundaries

The pilot is one app, Ledger, for one company; everything else in v2 is designed now and built later. Use ledger__ as the prefix everywhere (v2 mixes books__ and ledger__).

In scope for v1 pilot: runner, record book, gate, switchboard, assistant, proposals and waits, resolve and carry-out doors, gateway-lite, desk cards, NEOS app chat. Designed, built later: Matrix rooms, a2a and borrowing, registry publishing, packages, the improvement loop.

Principles (non-negotiable):

  • The job is the unit of work; nothing important lives in a process or a chat thread.
  • The model never holds a key, a database role or an execution token.
  • No model sits between a person's yes and the effect.
  • A yes binds to one fingerprint; any change needs a new yes.
  • Only a person, or a grant a person wrote, can approve.
  • Everything outside the prompt and the people the app works for is information, never instruction.
  • Every effect is written in the app's book and mirrored in the platform audit.

Trust zones, least to most trusted:

Untrusted input web pages, documents, room messages, other apps' words, borrowed skill text Nothing; read as data

The gate protects the app from its own model. The gateway protects every app from every other caller and from itself. Both are required.

Data model

Use one Postgres cluster with one schema per app (ledger.jobs) rather than prefixed tables in one schema. Schemas let GRANT USAGE and ALTER DEFAULT PRIVILEGES enforce the family boundary, keep tables out of Supabase's exposed public schema, and change nothing else in the v2 picture.

Roles: ledger_app (DML on schema ledger only), ledger_migrator (DDL on ledger, used only by the migration runner), neos_platform (schema neos only), neos_migrator. The assistant has no role.

Tenant isolation inside a family: every table carries company_id uuid NOT NULL. RLS policy company_id = current_setting('neos.company_id')::uuid; the backend sets it per transaction from the verified gateway token. The runner, which works across companies, uses a separate ledger_runner role with BYPASSRLS limited to the eight standard tables.

The eight standard tables (created by 001_standard.sql):

Table Key columns Notes
jobs id, company_id, source (task, room, timer, a2a), requester, task_id, status, created_at, parent_job_id status is text + CHECK, never an integer
steps id, job_id, seq, kind, summary, ability_key, input_hash, output_ref, created_at append-only; seq unique per job
waits id, job_id, kind (proposal, timer, a2a_task), ref_id, status, ready_at, claimed_by, claimed_until, expires_at claimed with FOR UPDATE SKIP LOCKED
proposals id, job_id, ability_key, ability_version, args jsonb, fingerprint, status, expires_at, superseded_by fingerprint = SHA-256 of JCS-canonical {key, version, args, company_id, job_id}
proposal_events id, proposal_id, event, actor, fingerprint_seen, at append-only history; status on proposals is a projection
operations id, job_id, caller, ability_key, idempotency_key, outcome, gateway_request_id, at one row per effectful call, matches gateway audit 1:1
facts id, company_id, subject, value jsonb, source, observed_at, job_id every fact carries where it came from
outbox id, company_id, event_type, payload, created_at platform pulls by cursor; never deleted before acked

v2 lists grants as a standard table. Move grants to the platform (neos.grants) because the gateway must see them to mint execution tokens; the app caches them read-only. Keep 8 by counting proposal_events in its place.

FAILED and UNKNOWN are missing from v2; both wake the job so the assistant can tell the person.

Job states: RECEIVED → RUNNING → WAITING ↔ RUNNING → DONE | FAILED | EXPIRED | CANCELLED. A job with an open wait is WAITING, never RUNNING.

Migrations: numbered, forward-only, immutable once run, expand-then-contract for zero-downtime changes, each proven on a populated copy (migrate.json marker). No rollback files; a bad migration is fixed forward.

Connections: each app backend holds a small lazy pool (max 5) through PgBouncer in transaction mode. The runner holds one direct session connection for LISTEN, because LISTEN/NOTIFY does not work through a transaction pooler.

Contracts

Every call into an app is one signed request from the gateway to L3; the app verifies it with the gateway's public key (JWKS) and never learns what a NEOS user or role is.

Gateway token (JWT, EdDSA, TTL 60 s): iss=neos-gateway, aud=<app>, sub=<caller: user | app | platform>, company_id, ability, ability_version, idem_key, jti, and for execution only proposal_id + fingerprint. L3 rejects a reused jti. An execution token is single-use and minted only when neos.approvals or neos.grants shows a matching fingerprint.

Headers on every call: Authorization: Bearer <token>, Idempotency-Key, Contract-Version, traceparent (W3C, for end-to-end tracing).

L3 endpoints (template-owned unless noted):

Endpoint Caller Purpose Idempotent on
POST /l3/tasks.open Platform A task from NeuralChat or another app becomes a job task_id
POST /l3/inbox.deliver Platform (appservice) A room message becomes a job or feeds a waiting one room event id
POST /l3/proposals.resolve Platform yes / no / change / withdraw against a fingerprint proposal_id + decision
POST /l3/proposals.execute Platform, execution token Carry out the approved thing once, read back proposal_id
GET /l3/outbox?after=<cursor> Platform Pull events: cards, results, task completions, operations cursor
POST /l3/abilities/<key> Platform or another app Run a read, or a write (proposal if gated) Idempotency-Key
GET /l3/live, /l3/ready Orchestrator Bounded liveness and readiness —
GET /l3/manifest Registry The declared contract —

App teams write only abilities/<key> handlers (reads and writes); everything else ships with the template.

Execute contract: check token, fingerprint and state APPROVED; set EXECUTING; call the door with a door-level idempotency key where the provider supports it; read back; set DONE, FAILED or UNKNOWN; mark the wait ready; return proof {outcome, external_ref, read_back, at}. A retried execute on a terminal proposal returns the stored proof and does nothing.

Platform-side approval workflow: neos.approvals is itself a state machine (RECORDED → RESOLVED → EXECUTED). A platform worker retries resolve then execute with backoff until terminal. This closes the v2 gap where a platform crash between (a) and (b) leaves a yes that is never carried out.

Outbox event types: job.acknowledged, proposal.created, proposal.expired, step.mirror, operation.recorded, task.completed, task.failed, a2a.requested. The platform consumes them to build desk cards, room mirrors, task completions and the audit trail.

Manifest (manifest.json) minimum: app key, version, contract version, abilities (key, version, kind read/write, input and output JSON Schema, gated floor, verifyWith), doors (scopes), uses (borrowed abilities with semver ranges), skills, packages, blocks.

Runner, waits and the assistant lifecycle

The runner is the only always-on part and holds no model; it turns inbound calls and timers into jobs, claims ready waits, and hands jobs to a pool of assistant workers.

Runner loops (src/runner/):

  1. Inbound — tasks.open / inbox.deliver insert a job in RECEIVED and an outbox job.acknowledged in one transaction; the HTTP response carries the job id within 300 ms p95.
  2. Waits — LISTEN neop_waits for hints; every 5 s, claim SELECT … WHERE status='ready' FOR UPDATE SKIP LOCKED LIMIT n, set claimed_by and claimed_until = now()+2 min. The poll is the truth, the hint is latency.
  3. Expiry — every 30 s, mark waits past expires_at (database time, never app clock) as expired, mark the proposal EXPIRED, set the wait ready so the job wakes to say so.
  4. Spawn — take a free worker from the pool (default 5 per app instance), start a fresh pi session, pass the job bundle, heartbeat every 15 s. A session that stops heartbeating loses its claim and the job is re-queued.
  5. Mirror — one step.mirror outbox event per step, deduplicated by (job_id, seq).

Job bundle handed to the assistant: job ask and requester, steps so far (last 20 in full, older ones as a rolling summary written to steps), relevant facts with sources, the wait answer and proof if resuming, the switched-on list with ask-first marked, eligible SKILL.md files, and a job token.

The job token is missing from v2 and is required. The agent container can reach its backend, so anything in that container could call the gate. The runner mints a token scoped to (company, job, allowed ability keys, expiry = claim window); the gate rejects calls without it or outside its scope.

Assistant limits per job: max 40 tool calls, max 15 minutes wall time per session, token and spend cap from the switchboard (default $5 per job, $50 per company-app per day). Hitting a cap ends the session with a FAILED step and a message, never a silent stop.

pi harness configuration (src/agent/extension.ts): built-in file, shell and fetch tools removed; the only tools are the gate-generated ones plus book.note, card.raise and job.finish; every tool result from a door or another app is wrapped as untrusted data; the model key comes from the LLM proxy as a per-app virtual key with a spend limit.

Switchboard, gate and policy

The switchboard is stored once on the platform, versioned per company and app; the gate evaluates it on every call from a local cache stamped with that version.

Setting resolution (strictest wins): effective = min(app_floor, company_setting, grant_override?) over the order off < ask_first < on. For a borrowed ability, also min with the owner app's setting at that company. A grant can turn ask-first into auto-approve within its limits; it can never turn off into anything.

Gate decision order for one call:

  1. Job token valid and ability in its scope? Else refuse.
  2. Ability exists in the manifest at the pinned version? Else refuse.
  3. Effective setting off? Refuse (it should not have been shown).
  4. Company rules (below) violated? Refuse with the rule id.
  5. Cap exceeded (per call and per period)? Refuse.
  6. Read, or write set to on? Execute, write operations and steps.
  7. Ask-first with a matching active grant within limits? Write a proposal already APPROVED by the grant, request an execution token from the gateway, execute through the same path.
  8. Ask-first otherwise? Write proposal + wait, return the proposal id.

Company rules as data, not code. v2 leaves "nothing on weekends" undefined. Use a closed rule set evaluated by the template: time_window (days, hours, company time zone), destination (internal-only, allow-list), amount_cap (currency, per call, per day, per month), recipient_cap, require_person (always ask-first for matching abilities). New rule types are template releases.

Money floor: amounts are integers in minor units (paise) with ISO currency; caps are per company per app per calendar month in the company's time zone unless stated.

Cache and invalidation: the gate caches the switchboard for 30 s and on each switchboard.changed event; every gateway token carries sb_version, and the gate refetches when the token's version is newer. This avoids an HTTP hop per call without letting a switch-off lag by more than one call.

Registry, skills, borrowing and packages

The registry is platform tables holding four entry kinds with one header (skill, ability, package, door); data lives in rows, code lives in a signed artifact fetched by hash. v2's model holds; the changes are about isolation, versions and review.

Registry tables: neos.registry_entries (key, kind, owner_app, version, offers, requires jsonb, body text, artifact_hash, signature, status), neos.registry_installs (company, host_app, entry_key, pinned_version, granted_at, granted_by), neos.acl (caller_app, ability_key, company, granted_by).

Four ways to share, one decision rule:

Need Mechanism Runs where Cost to add
Generic capability (email, calendar, PDF) Platform door Host backend, key per call Grant a scope
One step in another app's subject Borrowed ability Owner app, via gateway Grant an ACL row
Know-how using another app's abilities Borrowed skill (text only) Host assistant reads it; calls go to owner Grant ACL rows, minutes
Know-how plus its own handlers Package Host, inside a sandbox Install: migrations, tests
Multi-step work in another subject a2a task The other app, as a job Nothing new

Skill loading at spawn: a skill line loads only when it is on and every requires line is on at the company; otherwise it is skipped and the board shows the missing requirement. Skill lines are on/off only.

Package handler isolation (change from v2). v2 runs handlers in the host backend with a "narrow ctx". Inside one Node process that cannot be enforced; a handler can require('net') or read process.env. Run package handlers in a separate subprocess per package (Deno with --allow-none or Node with isolated-vm), talking to the host over a local RPC that exposes only ctx.book.step, ctx.book.fact, ctx.tables (package tables only, via host), and ctx.doors.<granted>. Hard limits: 256 MB, 10 s per call.

Package tables: <host>.nep_<name>_* in the host schema, owned by a <host>_nep_<name> role the host app role cannot write. Uninstall disables the package and keeps its tables; a drop is a separate, audited platform action.

Versions: abilities use semver; the owner's L3 must serve every version still pinned by any host. The registry refuses to retire a version with live pins until a 30-day deprecation window passes. A skill update that adds a requirement cannot move the pin until an admin grants it.

Publishing review: borrowed skill text enters another app's prompt, so a published skill is a prompt-injection vector from the publisher. Publishing requires a signature from a platform-held key after a person approves the diff on the desk, not only the author's signature.

Improvement loop: metrics.json signals aggregate per package version across hosts; the registry proposes the next SKILL.md; a person approves; hosts re-pin. Defer to after the second app ships.

Security model and deployment

Each app runs as two containers on a private network that only the gateway can reach; the model and the database role are never in the same process.

Container Holds Can reach Cannot reach
<app>-backend DB role, gateway JWKS, borrowed door keys (per call) Postgres via PgBouncer, gateway, vault, door providers The model
<app>-agent (pool of 5 workers) Job token, per-app LLM virtual key Its own backend's gate endpoint, LLM proxy Postgres, vault, internet, other apps
<app>-pkg-<name> (per package) Nothing Host backend over local RPC Everything else
neos-gateway Signing keys, ACL, idempotency ledger Every app's L3 The model

Enforce with network policy (egress allow-lists), not convention. Both a firewall rule and a failing test (network.test.ts) guard each row.

Threats and the control that stops each:

Threat Control
Prompt injection in a document or room Tool results wrapped as data; gate decides; ask-first effects need a person
Jailbroken assistant calls a gated ability directly Gate writes a proposal; execution needs a gateway-minted token
Bug in an app's gate Gateway checks ACL, approval row and fingerprint independently
Stale yes on an edited draft Fingerprint binding; a change supersedes the proposal
Replay of a signed call jti single-use, 60 s TTL, idempotency ledger
One company reading another's rows RLS on company_id, per-company room identities
Malicious package Signed + platform-reviewed, sandboxed subprocess, no network
Leaked committed credentials Secrets only in the vault; CI secret scanning; rotate on detection

Observability: one traceparent from the person's ask through gateway, runner, assistant session, gate and door; spans exported to the existing observability stack. Dashboards: job latency to ack (p95 < 300 ms), job completion rate, proposal answer time, execute outcome split (DONE / FAILED / UNKNOWN), spend per company-app per day.

Backups: one cluster means point-in-time recovery restores every app at once. Add a per-schema logical export nightly so one app or one company can be restored without rewinding the others.

Scrutiny: what v2 gets wrong or leaves open

Open decisions

Eight decisions close in Phase 0; each has a recommendation so review is a yes/no, not a blank page.

# Decision Recommendation Why
D1 Schema per app vs prefixed tables in one schema Schema per app Grants enforce the boundary; stays out of Supabase's exposed public
D2 Shared cluster vs dedicated DB per customised NEOP Shared by default; dedicated tier only on a contract that requires it The template code is identical either way; only the connection target changes
D3 Matrix in the pilot or later Later (Phase 3) The NEOS app chat covers the pilot; Matrix adds an appservice, identities and a second inbound path
D4 Gateway as a module or a service Module in the platform backend now; extract on an ops reason Same contract, less to run
D5 Package sandbox: Deno subprocess vs isolated-vm Deno subprocess Permission flags are explicit and testable; isolated-vm has no I/O model to lean on
D6 Fresh assistant: new container vs fresh session in a pooled worker Pooled worker, fresh session Cold start per job is seconds; the pool is already the NEOS worker model
D7 Canonical runtime repo (neos-neops vs neos-service-neop-builder) A new neop-template repo; Ledger cut from it The template must be upgradeable and never forked
D8 Grants in the app book or on the platform Platform (neos.grants), cached in the app The gateway must see them to mint execution tokens
